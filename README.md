# cyk-parser

A CYK parser for context-free grammars in Chomsky Normal Form that decides membership,
enumerates *every* derivation tree of an ambiguous string, and propagates rule
probabilities through those trees for stochastic parsing.

## The problem

Deciding whether a string can be generated by a context-free grammar cannot be done
greedily: a decision made early about how to group the first few symbols may only be shown
wrong much later. CYK sidesteps this by working bottom-up over every contiguous substring,
recording which non-terminals can generate it, and building longer spans out of shorter
ones — `n²/2` substrings, each split `n` ways, giving the familiar O(n³·|G|) recognition.

Recognition alone is the easy half. A grammar can be *ambiguous*, meaning the same string
has several distinct derivations, and for natural language that is the normal case rather
than a pathology. This parser therefore keeps, in every cell, the back-pointers describing
each way that cell's non-terminal could have been produced, so it can reconstruct all the
trees rather than just answer yes or no. Attaching a probability to each rule turns the
same structure into a PCFG parser, where each tree carries the product of the rules used to
build it.

## Design notes

**The grammar is indexed by rule body, not by head.** `CFG._index_rules` stores `SAB` as
`{"AB": {"S"}}`. The inner loop of CYK asks the question "which non-terminals produce this
pair of symbols?" once per split point, and indexing this way turns that into a single
dictionary lookup instead of a scan over the rule list. Bodies map to a *set* of heads
because the same body can have several — `AB` is produced by both `S` and `C` in the sample
grammar, and both have to survive into the cell.

**One table serves recognition, tree extraction and PCFG parsing.** Each cell maps a
non-terminal to a list of `TableEntry` records holding the body, the coordinates of the two
child cells, and the rule's probability. Recognition only asks whether the axiom is present
in the apex cell; `build_trees` walks the same back-pointers to rebuild derivations; and the
probability field is simply `None` in categorical mode. Because the entries are a *list*
rather than a single value, an ambiguous cell keeps all of its derivations, and
`build_trees` takes the cartesian product of the left and right children's trees — which is
exactly where ambiguity multiplies out.

**The table is triangular, indexed by (start, length − 1).** It is built as

```python
table = [[{} for _ in range(i)] for i in range(n, 0, -1)]
```

which counts `i` down from `n` to `1` and so allocates rows of length `n, n-1, … 1`. The
cell `table[i][j]` describes `sentence[i : i+j+1]`, so only `i + j < n` is meaningful, and
allocating exactly `n - i` cells in row `i` means the loops never need a bounds check. It
reads oddly at first glance, which is why the shape is spelled out in a comment in the
source.

Building the staircase rather than a full `n × n` square is also the difference between
allocating `n(n+1)/2` dictionaries and `n²` of them. Only `(n+1)/2n` of a square table would
ever be reachable — just over half, tending to half as the sentence grows — because a
substring starting at position `i` cannot have length `n - i + 1` or more.

**Entries are prepended, not appended.** `_fill_table` does `insert(0, entry)`. Split points
`k` are visited in increasing order, so inserting at the front reverses them, and
`build_trees` then emits the tree with the widest left child first. This is not cosmetic
book-keeping that has since become redundant — switching it to `append` still produces both
correct trees, but prints them in the opposite order to the one the assignment specifies.
There is a test pinning the order so that stays visible.

## Running it

The grammar is a text file with one rule per line, written without an arrow: `SAB` means
`S → A B`, and `Aa` means `A → a`. Non-terminals are uppercase letters, terminals
lowercase. For stochastic grammars each line carries a probability after a space. Strings
to parse are read from stdin, one per line.

```
$ python cyk.py -g g1.txt          # is the grammar in CNF?
yes

$ cat in.txt | python cyk.py -p g1.txt    # membership only
yes
no

$ cat in.txt | python cyk.py -t g1.txt    # every derivation tree
(S (A (B b) (A (B b) (A a))) (B b))
(S (B b) (C (A (B b) (A a)) (B b)))

no

$ cat in.txt | python cyk.py -s g1s.txt   # stochastic parsing
(S (A (B b) (A (B b) (A a))) (B b)) 0.02278
(S (B b) (C (A (B b) (A a)) (B b))) 0.02733

no
```

### Worked example

`g1.txt` is the grammar

```
S → A B | B C        A → B A | a        B → C C | b        C → A B | a
```

and `in.txt` holds `bbab` and `bba`. The first is ambiguous. CYK fills the base row with
the non-terminals producing each letter (`b` from `B`, `a` from `A` and `C`), then combines
spans. The apex cell ends up containing `S` by two different routes — splitting `bbab` as
`bba·b` and as `b·bab` — so `-t` prints two trees and `-p` prints a single `yes`. The
second string `bba` cannot be derived at all, so both modes print `no`.

Under `g1s.txt` the same two trees carry 0.02278 and 0.02733: the product of every rule
used along each tree. The second derivation is the more likely one, which is the sort of
judgement a PCFG exists to make.

The full transcript is in [commands.txt](commands.txt), and every line of it is pinned by a
test.

## Known limitations

- **CNF only.** The parser validates Chomsky Normal Form and refuses anything else; it does
  not convert a general context-free grammar into CNF. Grammars with ε-productions or unit
  rules must be converted by hand first, and a consequence of having no unit rules is that
  no string of length 1 is ever accepted by the sample grammar.
- **One letter per symbol.** Non-terminals are single uppercase letters and terminals single
  lowercase ones, capping the grammar at 26 of each. The format has no room for `NP` or
  `VP`, so this parses toy grammars, not real treebank ones.
- **Enumerating all trees is exponential in the worst case.** The number of derivations of
  an ambiguous string can grow exponentially with its length, and `-t` and `-s` materialise
  every one of them as a string. Recognition with `-p` is unaffected.
- **`-s` ranks nothing.** Stochastic mode prints all trees with their probabilities in table
  order; it does not select or even mark the most likely parse, so there is no Viterbi pass.
  Printed probabilities are truncated to five decimals, matching the assignment's output.
- **Duplicate rules are dropped with a warning**, keeping the first occurrence — which for a
  stochastic grammar means the first probability silently wins.
